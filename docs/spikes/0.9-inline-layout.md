# Spike: inline layout (0.9, unit 3)

Status: **done**. Every step passes, S2's p95 and S9 on a run alone on the machine on 2026-11-07.
Nothing here has run on a physical Android device. This report records what the spike
proved, per platform, before the inline UI in `docs/AARDINK_ROADMAP.md` §7.3 builds on it. Each step
lists its evidence: a test in the repository or a command's result.

**The question:** can text and rows outside the document be added per line, on demand, on all three
platforms, with every column mapping correct and the 5,000-line gates intact?

The spike is internal to `:editor` and adds nothing public: `checkAbiAll` has nothing to report for
it. The switch is `EditorView.injections`, null by default, and nothing in the library sets it.

## The model

- Injected text is spliced into the line's `AnnotatedString` as real characters, with a per-line
  `OffsetMap`. With nothing injected the map is `OffsetMap.Identity`, which answers with what it is
  given and allocates nothing.
- `LineLayout(result, map)` replaces `TextLayoutResult` as the `LineLayoutCache` value and in
  `VisibleLine`, and speaks document columns only. A column has three layout positions when text is
  injected at it, as `x|gy` shows for ghost text `g`: where a caret goes (`toLayout`), where the
  character is (`charIndex`), and where the range before it ends (`rangeEnd`).
- Added rows are hard line breaks inside the same paragraph, so `layout.lineCount` counts them and
  `VisualLineMap` is unchanged. `LineLayout` works out which rows hold no document column
  (`isInjectedRow`, `textRow`, `lastTextRow`) whenever something is injected and the layout has more
  than one row: a break makes such a row, and so does soft wrap when injected text fills one, so
  only the laid-out rows can tell. `hasCaret` and `columnOnRow` are what moving a caret asks: a row
  can hold a character and no caret, and a column found over injected text can have its caret on
  another row.

### How the tests were checked

Passing tests prove little until they have been seen to fail, and much of this was written by an
agent that was interrupted. So each piece of logic the plan names as a known cost was broken on
purpose, one at a time, and the spike's tests run against it: 32 mutants of `LineLayout`,
`OffsetMap`, `EditorView`, the drawing, the gutter, sticky scroll, the minimap, column selection and
the pointer. All 32 are now killed, on the JVM. Four survived at first, and each was a real gap
in the tests, not in the code, now closed:

- Nothing proved `setRows` runs without soft wrap.
- The fold placeholder test clicked too close to the hint to reach a position past the line.
- Column selection was tested only on lens rows, where a stray caret merges into the line's own
  range, and not on ghost rows below a line, where it does not.
- `rowEndX` was tested with the hint at the line's end, where the mixed-up columns happen to agree.

### What review found

That was not enough. **The first version of this report marked S5 and S7 Pass, and both were
wrong.** Review reproduced these on the JVM, and each is fixed:

- **Up and Down stuck on injected text under x.** `verticalMove` took the column under x on the
  target row, and over injected text that is the injection's column, whose caret can be on another
  row, usually the row the move started from. Down from column 1 of `foo()` with mid-line ghost text
  stayed at column 4 for good. It now asks `columnOnRow`, which lands on the row it reached.
- **A row filled by soft wrap counted as a text row.** Rows were only sorted when injected text had
  a line break, so a hint or ghost text wrapping onto rows of its own could stop the caret leaving
  the line, gave column selections a stray caret, and widened the highlight. Single-line ghost text
  and inlay hints were called shippable on this.
- **A middle press on a lens or ghost row threw**, in the pointer's coroutine: the box had no text
  row, and `SelectionSet.of` takes no empty list.
- **Injections landing between a scroll and its layout pass undid the scroll.** The anchor was the
  last pass's, so a jump to 3,000 px came back as 0.
- **`a page of rows lands on a text row` could not fail**, and the test called `all on a lens row`
  never was. The first asserted that a caret is on a row a caret can be on.

The mutants above missed all of this because the tests shared the code's assumptions: `walk` kept
x at 0, and the rows it expected came from `isInjectedRow`, so a wrongly sorted row agreed with
itself. The new tests take what is expected from the carets, or from raw `getLineForOffset`. Against
the old code 20 of them failed. Then 16 more mutants of these fixes were run on the JVM. Fifteen are
killed. Of the two that survived at first, one was a gap in the tests, now closed: nothing dragged a
box up from a press on a lens. The other was a guard of mine for a caret a fold's placeholder might
wrap away from the text; no scene reaches that, so the guard is gone.

### Running S9

Run alone on the machine, as these numbers only mean anything there; the results are below.

```pwsh
git switch wip/0.9-spike-perf
./gradlew :sample-web:npmPackage
cd tools/vite-smoke

pnpm build
node perf.mjs                    # switch off: the same-machine baseline, writes dist/perf.json

node perf.mjs --inline --lines 100000   # writes dist/perf-inline-100000.json
```

`pnpm` may need its full path, `%LOCALAPPDATA%\pnpm\bin\pnpm.cmd`. `--inline` sets
`window.__aardinkInlinePerf` before the editor is created, and `CodeEditorLayout` reads it through
`platform/InlinePerfHook.kt` when it makes the view. Compare `keyToIdleP95Ms` as a ratio between
`dist/perf.json` and `dist/perf-inline.json`, the two 5,000-line runs, because this machine reads
about 265 ms whatever the code. A run with `--lines` writes its own file, so the 100,000-line run
leaves those two alone; it answers whether the frames stay flat, and has no baseline unless
`node perf.mjs --lines 100000` is run too. For S2's p95, run `node perf.mjs` the same way on `v0.8.0`
and on this branch. The branch is thrown away afterwards.

Both runs must do the same work, so lenses start at line 19, below the comment `perf.mjs` clicks on:
a lens on line 0 would move every line down a row, and the same pixel would land on code, where
completion opens and takes keys of its own. Each run stops with an error unless the caret is on that
comment before the keys start, and the typed text is on that line after them.

## Found along the way

- **A text's empty last row is measured with the default font on skiko.** A lens above an empty
  line puts the line's only row last in the paragraph, and Skia measures that row without the
  row's style, so the caret came out the wrong height and place. `LineLayout.cursorRect` draws it
  from the row above, one pitch down. This is the one place where hard breaks needed a correction.
- **Row 0 can sit off the view's pitch.** `rowShift` counts from `getLineTop(0)` when a line has
  hard breaks, so added rows keep their own band. A line without breaks takes the old path.
- **`map(b) - 1` does land in injected text**, with a hint at the end of a range. `charBox` and
  `rangeEnd` are why each column has three positions, not one.
- **A minimap tile went stale when a lens moved.** Its short cut compared the document, the tokens
  and the row count, and a lens moving from one line to another changes none of them. It now
  compares `injectionVersion` too.
- **`injectionsChanged` moves the scroll at once.** Setting a flag for the next pass, as a document
  change does, would still lose a scroll arriving after the answer and before the pass, such as the
  next tick of a fling. So it captures the anchor where the view is now, and places the scroll and
  the height there and then. A frame a scroll has left is no longer trusted to measure its lines.
- **A row can hold a character and no caret.** The caret at a ghost's column is before the ghost, so
  a character after it has no caret before it. If the next column's caret is on another row, nothing
  is on that row: `isInjectedRow` says it is text, for painting, and `hasCaret` says no, for moving.
- **A browser test has two seconds.** The pixel sweep is about fifty renders a test, so
  it runs on the JVM, and the positions it depends on run in the browser through `InlineColumnsTest`.
  No assertion failed there; only the time ran out.

What the units after the spike still have to deal with:

- **Off-screen estimates count what is asked for, not what fits.** `estimateRows` has only the
  line's length and the `LineInjections`. A break in an injection that `fitted` later drops is
  counted until the line is laid out, then corrected. S10 holds for a host that injects what fits;
  units 15 and 16 should drop an injection past its line before answering.
- **A lens that wraps counts once for the minimap.** `rowsAbove` avoids a layout, so under soft wrap
  a lens wider than the view puts the minimap's bar a row high. Harmless, and only with wrap on.
- **A squiggle over a mid-line break** starts its later rows at the row's left edge, under any
  injected text before the first column on that row. Selections do not: they use exact runs. Only
  mid-line multi-line ghost text can reach this.
- **A column can only be reached from where its caret is.** Down onto text after mid-line ghost
  text lands after the first character there: the caret before that character is up on the ghost's
  first row. That is the model's meaning of `caretAfter`, and ghost text is short-lived, but unit 16
  should look at it with the real thing.
- **A selection does not cover a hint that crosses a wrap**, though it covers one on a single row:
  `rangePath` cuts where what is injected leaves the text either side on different rows.
- **A row of a line's highlight can still be only injected text** when it is between two rows of
  text, as with a break: `textRow` to `lastTextRow` is one band. Rows after the last text row are out.
- **A closed fold's placeholder wrapped onto its own row, on a line with injections, counts as
  injected.** Down passes it and the highlight stops short of it. Without injections it is a text row.
  Harmless, but the two differ.
- **`onDocumentChange` has the stale anchor `injectionsChanged` had**, from before this unit: a scroll
  between an edit and its pass is lost. Edits are not driven by scrolling, and that path is the
  switch-off one, so it was left.
- **`injectionsChanged()` with no range walks every line.** That is a lookup per line, not a layout,
  but units 15 and 16 should pass the range they changed.
- **Whatever answers `injections` must be up to date when `onDocumentChange` runs**, because the row
  map is spliced there. `TrackedRanges` moves with the same change, but the order must be checked.
- **Robolectric is not a device.** The comment on `rowShift` records that some Android devices
  space rows further apart than `lineHeight`; Robolectric shows a shift of 0, so that branch is
  exercised with a real shift only on skiko. It needs one look on a real phone before code lens
  ships on Android, as do Gboard and Samsung Keyboard on a line with a hint.

### S2 and S9 results

Run on 2026-11-07, with no build running: three rounds, interleaved so that drift hits every package
alike, 30 keys a run. Medians of three, in ms. `feat/0.9` at `1229ce3` has all of 0.9 merged so far,
with the switch off, and was not part of the plan: it is what ships.

| Key to change, p95 | 3.5 | 3.3 | 5.4 | 3.9 | 20 (target) |
| Scroll frame, p95 | 16.8 | 16.8 | 16.8 | 16.8 | 20 |

At 100,000 lines, one run each:

| Measure | Switch off | Inline load |
| --- | --- | --- |

What these numbers do not settle:

- Key to idle sits near 240 ms at 5,000 lines on every package: it includes the 150 ms tokenize
  debounce and the pass after it. A 10% limit there is about 25 ms, so it cannot see a smaller cost.
  Key to change is the sharper measure, and the load does not move it at this size.
- `feat/0.9`'s key to change read 5.4, 13.8 and 3.9 against v0.8.0's 3.3 to 3.8. A p95 of 30 keys is
  nearly the worst key, so one slow key moves it, and three runs cannot tell that from a small real
  cost. It is under the target either way. The check on the finished 0.9 should look at it again.
- The minimap's cost is a difference clamped at zero, which is why v0.8.0 reads exactly 0.0. About
  0.5 ms with the switch off may be real.
- At 100,000 lines the load costs more than at 5,000: key to change 2.8 times, mount to idle about
  140 ms more, and a longest task of 172 ms. All are within their targets but mount, which has no gate
  at this size. One run each, and the hook answers for every line it is asked about, which the real
  hosts of units 15 and 16 may not. Worth measuring again with them.
- Scroll frame reads 16.8 ms everywhere: that is the display's 60 Hz, so it shows no frame was
  missed, not how much room is left.

## Decision

**Every step passes, so nothing in the plan's "If steps fail" table applies.** S5 and S7 failed in
review and pass now that the faults are fixed. Had they stayed as they were, inline text would have
shipped unwrapped only, and multi-line ghost text and code lens would have needed integer rows. S9
passes without a hint cap.

| Feature | Rests on | Decision |
| --- | --- | --- |
| `before`/`after` text | S3, S4, S5, S8 | **Can ship** |
| Inlay hints | S3, S4, S5, S8, S9 | **Can ship**, with no hint cap |
| Single-line ghost text | S3, S4, S5, S8 | **Can ship** |
| Multi-line ghost text | S6, S7 | **Can ship**, with a device check on Android. No integer-row fallback is needed |
| Code lens | S6, S7, S10 | **Can ship**, with a device check on Android |

The model stands as designed: per-line `OffsetMap`, `LineLayout` as the only reader of a layout, and
added rows as hard breaks inside the paragraph. `VisualLineMap` did not change. The unknown that
could have moved multi-line ghost text and code lens to 0.10, Compose's hard breaks with
`softWrap = false`, is answered: they work on all three platforms.

What is left is the device check on Android, before code lens or multi-line ghost text ships there.

## After the features were built

What became of the notes above once inlay hints, code lens and ghost text used this layout:

- **A lens that wraps** is now counted by `estimateRows` before its line is laid out, so a phone keeps
  the height of soft-wrapped lenses. The minimap's `rowsAbove` still counts one row for it.
- **A column after mid-line ghost text** is no longer a trap: Up and Down end ghost text before they
  move, so Down from `foo(|)` goes to the next line. Column selection by keys does the same; by mouse
  it still goes by the rows on screen.
- **Hosts answer only what fits.** Columns come from offsets, so none is past its line, and anything
  past the 10,000-character cut is dropped before answering. `injectionsChanged` has an internal
  overload taking only the lines that changed, and nothing walks every line.
- **Still open:** the device check on Android, for the `rowShift` branch, code lens, multi-line ghost
  text and keyboards composing on a line with a hint; and the 100,000-line timing with the real hosts,
  which `perf.mjs --hints --lines 100000` can now measure but has not.
