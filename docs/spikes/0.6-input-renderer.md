# Spike: own text input and virtualised drawing (0.6.0, PR 0)

Status: **in progress**. This report records what the spike proved, per platform, before the
renderer work in `docs/AARDINK_0.6_PLAN.md` §6 (PR 5 onward) builds on it. Each step lists its
evidence: a test in the repository, a measurement, or a manual check with the device and date.

The spike was built as the real PR 5 and PR 6 code on `v0.6-uplift`, behind the
`EditorRenderer` switch, rather than on a throwaway branch: the pieces it has to prove (the
`skikoMain` source set, the input request, the window buffer, the view model) are exactly the
ones those PRs ship, and the switch keeps the text field the default until PR 7.

## Findings before any code

From Compose Multiplatform 1.12.1's sources jars and `jb-main` (read 2026-09-27):

| Question | Finding |
| --- | --- |
| Can a custom node receive text input on every platform? | Yes. `PlatformTextInputModifierNode` and `establishTextInputSession { startInputMethod(request) }` are public, stable and common. The request type is an `expect interface` with no common members, so it is built per platform. |
| Android | `PlatformTextInputMethodRequest` is a stable `fun interface` returning an `InputConnection`; the session exposes the `View` for `InputMethodManager`. Compose's own `StatelessInputConnection.android.kt` is the reference for batch edits and IME quirks. |
| Desktop and web (skiko) | The request is a public interface whose members are `@ExperimentalComposeUiApi`: `value`, `state: TextEditorState`, `imeOptions`, `onEditCommand`, `onImeAction`, `textLayoutResult`, `focusedRectInRoot`, `textFieldRectInRoot`, `textClippingRectInRoot`, `unclippedTextOffsetInRoot`, `editText`. Compose's own `TextInputSession.skiko.kt` applies `onEditCommand` with the public `EditProcessor` onto a `TextFieldValue`, and implements `TextEditingScope` over a buffer in about 80 lines: the template to follow. |
| Will CMP 1.13 break it? | `jb-main` only adds `editorToken: Any?` to the skiko request, with a default getter: source-compatible. 1.13's web input writes into a `contenteditable` backing element instead of a `<textarea>` (#3167); the request contract is unchanged. |
| Does the whole document have to go into the IME buffer? | No. On the web, `value()` is written into the hidden input element on every change, so it gets a window around the caret (§4.1 of the plan). Android and desktop only ever read bounded slices. |
